# HR Project Instructions

## Назначение

Этот репозиторий является рабочим блоком HR Control Tower и связанных сервисов подбора. Любые изменения должны сохранять данные кандидатов, историю синхронизаций и работоспособность production-маршрутов.

## Источники истины

Перед изменением кода или структуры читать в таком порядке:

1. `PROJECT_IDEA.md` — бизнес-цель, пользователи и ограничения.
2. `SPEC.md` — требования, данные, API, безопасность и критерии приёмки.
3. `AGENTS.md` — правила выполнения работ.
4. `docs/admin/README.md` — карта доступов, архитектура и runbook для эксплуатационных работ.
5. `docs/features/FEATURE_<name>.md` — границы текущей функции, если файл существует.
6. Код, тесты, миграции и deployment-конфигурацию.

Если документация противоречит коду, не выбирать молча одну сторону. Зафиксировать конфликт и применить минимальное безопасное решение.

## Рабочий процесс

Использовать цепочку:

`Discovery -> PROJECT_IDEA.md -> SPEC.md -> AGENTS.md -> FEATURE_*.md -> Build -> Review -> Deploy`

Для каждой задачи:

1. Определить текущую фазу и критерии приёмки.
2. Изучить затронутые файлы и состояние рабочего дерева.
3. Сделать минимальное связное изменение без стороннего рефакторинга.
4. Добавить или обновить тесты соразмерно риску.
5. Выполнить доступные проверки, изучить diff и production-состояние, если был деплой.
6. Сообщить изменённые файлы, проверки, допущения и оставшиеся риски.

Не менять публичные API без явного решения. Не менять схему БД без миграции. Не удалять тесты ради успешной проверки. Не сохранять реальные ключи, токены и коды доступа в репозитории, логах или ответах.

## Подбор, презентация и Telegram

Для задач, связанных с `/present`, `/rookies`, фотографиями и описаниями кандидатов, Supabase Storage, Edge Functions `hr-present`/`hr-rookies`, а также пользователями `tg-hr-bot`, обязательно использовать локальный скилл:

`./.agents/skills/podbor-hr-support/SKILL.md`

Администраторские корректировки, деплой и восстановление выполнять по `./docs/admin/README.md`.

Подробные процедуры:

- авария фото и презентации: `./.agents/skills/podbor-hr-support/references/photo-presentation-incident.md`;
- добавление, разблокировка и переименование пользователя Telegram: `./.agents/skills/podbor-hr-support/references/telegram-users.md`.

Критические ограничения для этого блока:

1. Не запускать `supabase db push`, `supabase migration repair`, массовые `update`, архивирование или удаление карточек для исправления отображения.
2. Сначала проверять `photo_path`, объект в bucket `candidates`, HTTP-ответ и состав production-деплоя.
3. Не деплоить Next.js, если build не содержит `/present`, `/rookies` и `/api/photo`.
4. Не считать отсутствие картинки потерей файла до проверки БД и Storage.
5. Не делать пользователя Telegram администратором без отдельного явного решения владельца.
6. После изменения проверять production-маршруты, HTML, фото-прокси и логи ошибок.

## Критерии завершения HR-инцидента

Работа по восстановлению фото и презентации завершена только когда:

- `/present` и `/rookies` доступны в production;
- карточки с заполненными данными показывают фото, описание и даты;
- `/api/photo?path=...` возвращает `200` и `image/*`;
- нет новых 5xx в Vercel и Edge Functions;
- пользователь Telegram проходит `/кто` и может открыть черновик карточки без создания лишней production-записи.
