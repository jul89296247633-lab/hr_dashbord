# [ЗАГОТОВКА] Feature Spec #3 — Сводная таблица вакансий в стиле Google Sheets «Data»

> **Статус:** DRAFT / вводные зафиксированы. Полная спека + реализация — отдельной сессией.
> **Проект:** HR Control Tower · **Дата фиксации:** 2026-05-31
> **Цель:** переверстать `/vacancies/admin` под вид рабочей Google-таблицы «Data» (сводный первоисточник вакансий) — те же 16 колонок по порядку, цветовое кодирование строк по статусу, цветной приоритет, со сменой статуса прямо в таблице (сохранить текущий inline-edit).

**Итог:** 11 ✅ есть (часть под другим именем), **3 ❌ добавить**, **2 🔶 развилки**.

### Ответы на контрольные вопросы
1. **Причина появления** — поля нет. Нужен новый enum `appearance_reason`.
2. **Пояснение/основание** — есть `request_reason` (текст причины заявки). Развилка: переиспользовать его как «Пояснение» или завести отдельное поле (§3, развилка A).
3. **TTF** — есть колонка `days_to_close`. Это и есть TTF (`closed_at − opened_at`). Отдельное вычисление в UI не нужно, но проверить при реализации, что значение проставляется на закрытии (если нет — считать на лету).
4. **ФИО кандидата** — поля нет. Нужен `candidate_name` (text). Связь с `hired_employees` НЕ обязательна на первом шаге (Data ведёт ФИО строкой).
5. **Комментарий** — отдельного `vacancies.comment` НЕТ. Нужен новый `comment` (text). Не путать с `request_reason`.

## 2. Новые поля БД (миграция, отдельной сессией)

```sql
-- 4. Причина появления вакансии
CREATE TYPE public.appearance_reason AS ENUM
  ('dismissal', 'replacement', 'expansion', 'internal_transfer', 'other');
ALTER TABLE public.vacancies ADD COLUMN appearance_reason public.appearance_reason;

-- 15. ФИО нанятого кандидата (строкой; связь с hired_employees — позже, если нужно)
ALTER TABLE public.vacancies ADD COLUMN candidate_name text;

-- 16. Свободный комментарий (≠ request_reason)
ALTER TABLE public.vacancies ADD COLUMN comment text;
```
> Маппинг enum→RU для UI: dismissal=Увольнение, replacement=Замена, expansion=Расширение, internal_transfer=Внутр. перевод, other=Другое.
> RLS/гранты не трогаются (колонки на существующей таблице под RLS). Обновить `vacancyCreateSchema`/`vacancyUpdateSchema` + типы `database.ts`/`index.ts`.

## 3. Развилки (требуют решения до реализации)

**Развилка A — «Пояснение»:**
- Вариант A1: «Пояснение» = существующий `request_reason` (переиспользовать, не плодить поля).
- Вариант A2: завести отдельное поле `appearance_note` (text), а `request_reason` оставить под обоснование заявки.
- *Зависит от:* совпадает ли смысл «Пояснения» в Data с обоснованием заявки на согласование.

**Развилка B — «Менеджеры» (мн. ч.):**
- В Data в ячейке может быть несколько менеджеров; в БД `manager_id` — один FK.
- Вариант B1: оставить один `manager_id` (показывать одного; мн. ч. в Data — редкость/со-ведение).
- Вариант B2: many-to-many (`vacancy_managers`) — крупное изменение модели, ломает текущие фильтры/дашборды по `manager_id`.
- *Рекомендация для обсуждения:* B1 на первом шаге, B2 — отдельной спекой если со-ведение реально частое.

## 4. Цветовое кодирование

### Статус — перенести с бейджа на строку (`TableRow`)
Текущая палитра (`STATUS_VARIANTS`, [AdminVacanciesClient.tsx:86](../src/components/vacancies/AdminVacanciesClient.tsx#L86)) — **переиспользовать**, перенеся фон со span-бейджа на всю `<TableRow>`:

| Статус | Класс (текущий) |
|--------|-----------------|
| active (Активна) | `bg-green-100 text-green-800` |
| probation (Стажировка) | `bg-amber-100 text-amber-900` |
| paused (Пауза) | `bg-yellow-100 text-yellow-800` |
| closed (Закрыта) | `bg-slate-100 text-slate-600` |
| cancelled (Отмена) | `bg-red-100 text-red-800` |
| draft (Черновик) | `bg-blue-100 text-blue-800` |

> При переносе на строку — приглушить насыщенность (например `bg-*-50`), чтобы текст ячеек оставался читаемым; на бейдже статуса в колонке «Статус» цвет можно оставить ярче. Решить, кодировать ли ТОЛЬКО статусом или комбинировать с конфиденциальностью (например, рамка/иконка для `confidential`).

### Приоритет — добавить цвета (сейчас цвета нет)
- высокий → красный, средний → жёлтый, низкий → зелёный (бейдж в колонке «Приоритет»). Свериться с реальными значениями `priority` в БД при реализации.

## 5. Поведение / scope переверстки `/vacancies/admin`

- **16 колонок по порядку Data** (см. §1). Город ← `location`, Формат ← `confidentiality`, TTF ← `days_to_close`.
- **Сохранить inline-edit статуса** — текущий `VacancyStatusCell` (popover статусов; `closed` → выбор даты закрытия → PATCH). Не ломать.
- Сохранить прочий inline-edit ячеек (`VacancyEditableCell`), где уместно (Название, Подразделение, Заказчик, Кол-во, Комментарий, ФИО кандидата).
- **Цвета строк по статусу** (§4) + цветной приоритет.
- Учесть простые доработки, которые НЕ были применены (решение пользователя — сюда или отдельно):
  - поле «Подразделение» в модалку «Добавить вакансию» (datalist);
  - фильтр по подразделению (Select + `subdivision` в `vacancyAdminQuerySchema` + `eq`).
- Это **переверстка существующей страницы**, не новая (текущая `/vacancies/admin` уже даёт список+inline-edit+фильтры+CSV; расширяем колонки/поля/цвета).
- Роли/доступ — без изменений (head/admin правят; executive — read-only без имён менеджеров, EC-09).
